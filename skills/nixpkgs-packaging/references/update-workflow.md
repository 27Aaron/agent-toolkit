# 更新脚本与生成数据

用于新增或修改更新器、外置版本/hash 数据的任务。优先使用目标仓库已有工具；工具能力以目标版本为准，参考 [官方链接](official-links.md)。

## 通用更新器 nix-update

`nix-update` 是 Nixpkgs 的首选更新工具，支持标准 fetcher 和多数语言依赖输出（`goModules`、`npmDeps`、`pnpmDeps`、`cargoDeps` 等）。

- 只重写 Nix 文件里的字面量；数据放在 JSON 等外部文件时无法更新，需要自写脚本或把字面量移回 `package.nix`。
- 同一源码派生的多个固定输出用 `--subpackage <属性名>` 一并更新（如 Go 后端加前端）；子包必须能通过属性路径访问（`passthru` 或顶层属性）。
- 接入方式为 `passthru.updateScript = nix-update-script { extraArgs = [ ... ]; };`，简单包可以不写。
- 在已是最新的包上再次运行应不产生 diff；`--version=skip` 只刷新 hash。

## 选择数据布局

版本和少量 hash 字面量保留在 `package.nix` 通常最简单。多个平台或依赖输出需要统一生成时，可使用同目录 JSON，并通过 `lib.importJSON ./hashes.json` 加载。字段名称应能识别对应输出；不要仅为统一风格迁移已有数据。

修改布局前确认通用更新器是否支持该表达式和语言依赖；只有它无法正确读写目标值时才添加专用更新器。移走字面量后，不保留实际失效的 `passthru.updateScript`。

脚本应接入 `passthru.updateScript` 或项目已有更新入口，并通过该入口验证。直接执行的脚本需有正确 shebang 和可执行权限；由解释器调用时不强求可执行位。声明运行时工具依赖，不依赖作者机器上偶然存在的命令。

## 更新过程

1. 确定目标版本：接受用户或调用者指定的版本；未指定时才发现上游 release，并遵循既有发布渠道和预发布策略。
2. 根据实际调用方式定位可写 checkout：源码树内的脚本可从自身位置定位包目录；由 Nix 生成、运行于 store 中的脚本应使用调用者提供的工作树位置或约定的工作目录，不能从 `$0` 推断可写源码目录。需要 Git 根目录时，用 `git -C` 指向已确认的工作树内目录再调用 `rev-parse --show-toplevel`；独立项目无需强行依赖 Git。
3. 记录脚本启动前将修改的目标文件内容和存在状态，包括用户尚未提交的修改。优先在临时副本中计算和验证数据。
4. 按实际依赖图获取输出 hash：通常先源码，再消费该源码的依赖输出；不固定假设前端一定先于 Go/Rust。预取参数必须与 derivation 一致。
5. 必须借助构建获取 hash 时，只给当前输出写入标准 fake hash。JSON 字符串使用 `sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=`；Nix 表达式可使用 `lib.fakeHash`。核对 mismatch 所属 derivation 后再取 `got`，不要提取日志里任意一个 hash。
6. 检查版本、数据字段及所有受影响的 hash，重新求值相关 derivation。单文件通过同目录临时文件加 rename 原子替换；多文件更新需要完整备份和失败恢复，不能把逐文件 rename 宣称为整体原子更新。

## 失败和并行执行

- 失败或中断时，清理临时资源，仅恢复本次脚本修改的文件到启动前状态；不要用 `git reset` 或 `git checkout` 恢复整个工作区。
- 如果执行期间目标文件被其他操作修改，停止并报告冲突，不用旧备份覆盖新修改。对同一包可能发生的并发更新使用适当的互斥或冲突检测。
- Nixpkgs 更新任务可能并行处理不同软件包。使用独立临时目录，不修改共享配置或无关文件，不假定调用者的当前目录。
- 网络或构建失败时保留诊断；同一原因重复失败且没有新依据时停止，不无限重试，也不将 fake hash 留作最终结果。
- 更新脚本不自行 commit 或 push。

## 验证

检查解释器语法、JSON 语法和必需字段；通过真实更新入口验证成功更新、同版本再次运行不产生无意义差异，以及失败后恢复启动前内容的行为。涉及多输出时检查 hash 与输出的对应关系。使用隔离的临时工作副本验证失败路径，避免污染真实工作区；需要网络或完整构建而环境不可用时报告未验证项。
