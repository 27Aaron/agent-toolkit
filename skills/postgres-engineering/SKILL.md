# PostgreSQL 工程

以项目的 PostgreSQL 主版本、迁移工具、命名约定和权限模型为准。围绕当前任务给出能验证的改动；不要把供应商默认值或经验口诀当成通用规则。

## 先取得必要上下文

优先从用户材料、仓库配置、迁移历史、调用方和已有诊断结果取证。只收集会改变当前决策的信息：

| 任务 | 关键上下文 |
| --- | --- |
| Schema / SQL 实现 | 业务不变量、相关表/约束/索引、真实调用方式和参数类型 |
| 性能诊断 | SQL、代表性参数、数据规模/分布、执行计划、调用频率与延迟目标 |
| 迁移 | 主版本、工具事务模式、表大小、并发写入、应用兼容窗口和锁预算 |
| 权限 / RLS | 实际登录及执行角色、GRANT、全部适用策略、身份/租户上下文来源 |
| 连接 / 维护 | 池化器及模式、应用副本数、连接/锁/事务指标、复制与清理状态 |

缺少执行计划不妨碍修复已能证明的 SQL 或权限问题；把性能建议标为待验证假设。仅在缺失事实会改变正确性、执行范围或方案选择时询问用户，并继续不依赖这些事实的工作。

## 实现与验证

- 用户要求修改时，更新项目实际使用的 SQL、迁移或调用代码，并运行相关检查；说明性示例不能替代实现。
- 先保证结果集、排序、NULL 语义、约束和权限正确，再比较性能。索引建议要对应筛选、连接或排序需求，并考虑已有索引与写入代价。
- 性能改动使用可比的数据、参数和角色验证；区分估算与实测，不能仅凭 cost 降低或出现 `Index Scan` 声称优化成功。
- RLS 用实际访问角色验证允许与拒绝路径；并发逻辑需要能暴露竞争条件的多事务验证；迁移验证工具事务模式和应用兼容性。
- 数据库或代表性数据不可用时，完成静态检查，明确未执行的验证及所需条件，不声称已经通过运行验证。

SQL 使用项目实际的 Schema 和对象名。参考中的 `app.*` 是示例对象，`$1` 等是驱动绑定参数；在 `psql` 中应使用 `PREPARE` / `EXECUTE` 或明确的脱敏字面值。动态标识符不能用值参数代替，应使用允许列表和正确引用。

## 执行边界

- 编写、审查迁移与执行线上变更分别判断。沿用用户已授权的环境和操作范围，不重复索取已有授权，也不把改文件的请求扩大为生产执行。
- `EXPLAIN` 默认不执行被解释的语句；`EXPLAIN ANALYZE` 会执行，包含调用写入函数的 `SELECT`。实际运行前检查副作用、负载和超时；回滚不能撤销序列消耗或外部副作用。
- 生产权限、全局配置和数据清理的实际变更需有相应授权及与风险匹配的恢复安排。不要默认扩大权限、禁用 RLS、执行 `ALTER SYSTEM` 或用 `CASCADE` 消除依赖错误。
- `IF NOT EXISTS` 不验证已有对象定义；同名对象定义冲突或处于无效状态时，先核对目录和迁移状态，再决定恢复步骤。
- 示例和交付证据移除连接凭证及用户数据；保留诊断所需的类型、分布和查询结构。

## 交付

- 实现：说明改了什么、依据和验证结果；迁移或运行配置变更再补充执行顺序、锁/资源影响及恢复方式。
- 审查：按实际影响排序，提供文件/对象位置、触发条件、证据和最小修正；把已确认问题与待验证假设分开。
- 简单查询或局部修正保持简短；不为没有迁移的任务强制交付回滚方案或完整运维清单。
