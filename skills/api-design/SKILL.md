# REST API 设计

设计语义清晰、行为一致、便于客户端使用和演进的接口。优先遵循用户要求和项目既有契约；下文的命名、响应结构和参数形式是无既有约定时的建议，不是 HTTP 强制标准。发现协议语义问题时说明影响，不要仅为统一风格破坏已发布接口。

## 工作方式

- 先确定任务是设计、审查还是实现。用户已提供充分契约或代码时直接分析；需要仓库上下文时，只查阅相关路由、数据模型、鉴权逻辑、错误处理和 OpenAPI 文档。
- 明确调用方、资源关系、权限边界和兼容性要求。缺少信息时先给出合理默认值；只有答案会实质改变契约或引入破坏性变更时才询问。
- 新接口先确定方法、路径、输入、成功与失败响应，再考虑分页、重试等适用机制。已有接口优先复用项目的校验器、序列化器和错误处理中间件。
- 仅审查时给出具体问题、触发条件、影响和最小修正建议，区分协议错误、兼容性风险与风格偏好；不自动扩展为全量重构。

## 资源与路径

集合通常使用复数名词，路径使用小写字母，多词资源可用连字符；单例资源如 `/profile` 可以使用单数。沿用已有的路径前缀和版本方案，示例中的 `/api/v1` 不是必需结构。

```text
GET    /api/v1/users                    # 查询集合
POST   /api/v1/users                    # 创建资源
GET    /api/v1/users/{user_id}           # 查询单个资源
PUT    /api/v1/users/{user_id}           # 完整替换
PATCH  /api/v1/users/{user_id}           # 局部修改
DELETE /api/v1/users/{user_id}           # 删除资源
GET    /api/v1/users/{user_id}/orders    # 查询归属集合
POST   /api/v1/orders/{order_id}/cancel  # 明确的业务操作
```

- 用查询参数表达筛选，如 `/orders?status=pending`，避免 `/getOrders` 这类重复表达 HTTP 方法的路径。
- 仅在归属关系有意义时嵌套资源；独立访问的资源可提供顶层路径。嵌套查询同时校验父子关系和访问权限，避免只按子资源 ID 查询。
- 取消、发布等操作可建模为状态更新、子资源或动作端点，根据业务约束选择；不要为了消除动词而隐藏操作语义。

## HTTP 方法与状态码

安全方法不请求改变业务状态；幂等指相同请求重复执行的预期效果相同，不要求每次响应相同。例如重复删除可以先返回 `204`，再返回 `404`。方法语义依据 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)。

| 方法 | 安全 | 幂等 | 主要用途 |
| --- | --- | --- | --- |
| `GET` | 是 | 是 | 读取资源 |
| `HEAD` | 是 | 是 | 获取响应元数据，不返回响应体 |
| `POST` | 否 | 不保证 | 创建资源或执行操作 |
| `PUT` | 否 | 是 | 在目标 URI 创建或完整替换资源 |
| `PATCH` | 否 | 不保证 | 按补丁语义局部修改 |
| `DELETE` | 否 | 是 | 删除资源 |

`PATCH` 可以设计为幂等，但递增、追加等操作不天然幂等；一组补丁必须原子应用，失败时不能保留部分修改。明确媒体类型、缺失字段和 `null` 的含义。[PATCH 规范](https://www.rfc-editor.org/rfc/rfc5789.html#section-2)

采用 `application/merge-patch+json` 时，省略字段表示不修改，`null` 表示删除成员，数组整体替换；需要将字段设为 JSON `null` 时，不要混用这些语义。[JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396.html#section-2)

按实际结果选择状态码，不将所有结果包装为 `200`：

| 状态码 | 使用条件或处理要求 |
| --- | --- |
| `200` | 成功并返回结果；空集合也可返回 `200` 和空数组 |
| `201` | 已创建资源；创建接口通常通过 `Location` 指向新资源 |
| `202` | 已接受但尚未完成；提供任务状态或结果查询方式 |
| `204` | 成功且无响应体，不能附带 JSON |
| `400` | 请求格式错误；也可按项目契约承载输入校验错误 |
| `401` | 缺少有效认证凭据，包含适用的 `WWW-Authenticate` |
| `403` | 拒绝访问；需要隐藏资源存在性时可按统一策略用 `404` |
| `404` | 目标资源不存在，或按权限策略隐藏其存在性 |
| `405` | 资源不支持该方法，包含 `Allow` |
| `409` | 唯一性约束或当前业务状态冲突 |
| `412` | `If-Match` 等请求前置条件不成立 |
| `413` / `415` | 请求内容过大 / 不支持该媒体类型 |
| `422` | 内容类型和语法可理解，但指令在语义上无法处理 |
| `429` | 调用方触发限流，参见下文 |
| `500` | 未预期的服务端错误 |
| `502` / `504` | 网关收到无效上游响应 / 等待上游超时 |
| `503` | 服务暂时不可用；可提供 `Retry-After` |

`400` 与 `422` 的校验错误划分保持一致，不为采用某个状态码单独破坏既有契约。除单独说明的扩展码外，状态码语义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)。

## 请求与响应契约

- 沿用字段命名风格，明确类型、必填项、默认值、长度或范围、枚举、只读字段，以及缺失值与 `null` 的区别。
- 日期时间包含时区；大整数和精确小数明确序列化方式。金额可用最小货币单位整数或十进制字符串，并注明币种与精度。
- 成功响应可直接返回资源，也可使用 `data` 包装；需要分页元数据时可使用 `data`、`meta`、`links`。不要在同类接口间随意切换，也不在 `204` 中套用包装。

```json
{
  "data": {
    "id": "usr_123",
    "name": "张三",
    "created_at": "2026-09-01T10:30:00Z"
  }
}
```

### 错误响应

复用既有错误结构。新项目需要通用格式时，可采用 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)，响应类型为 `application/problem+json`：

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "请求参数校验失败",
  "status": 422,
  "detail": "请修正以下字段后重试。",
  "errors": [
    {
      "pointer": "/email",
      "code": "invalid_format",
      "message": "请输入有效的电子邮箱地址。"
    }
  ],
  "request_id": "req_123"
}
```

- `type` 标识稳定的问题类型；`status` 若存在，服务端生成时必须与实际 HTTP 状态码一致。客户端依据类型或稳定错误码分支，不解析可能翻译或调整的人类可读消息。
- 上例的 `errors`、`code`、`message`、`request_id` 是项目扩展字段，不是 RFC 必填项；`pointer` 按 JSON Pointer 定位请求体字段。使用自定义 `error` 包装时同样保持稳定结构，不强行迁移旧接口。
- 校验错误尽量定位到字段；未预期错误只提供可公开的信息和追踪标识，不泄露堆栈、SQL、凭据或敏感数据。

## 分页

可能持续增长的集合应在初版考虑分页；固定且有明确上界的小集合可直接返回。选择依据是访问方式、查询成本和一致性要求，不设固定数据量门槛。

| 方案 | 适用场景 | 主要限制 |
| --- | --- | --- |
| 页码或偏移量 | 需要跳页、数据量和查询成本可控 | 深偏移开销大，并发插入或删除可能导致重复或遗漏 |
| 基于排序键的游标 | 顺序遍历、信息流、大集合 | 通常不能任意跳页；需要稳定排序和匹配的索引 |

- 定义页大小默认值与上限、越界处理和结束标记；`total` 按需提供，并说明是精确值还是估计值。
- 两种方式都需要唯一确定的排序，例如 `created_at DESC, id DESC`；仅按可能重复的时间排序会导致分页边界不确定。[LIMIT 与 OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)
- 游标作为客户端无需解析的令牌，校验格式并绑定筛选、排序和访问范围；Base64 不是加密或完整性保护，必要时采用签名或服务端令牌。翻页时仍需重新鉴权，不能把游标当作访问凭据。[Google AIP-158 的游标建议](https://google.aip.dev/158#opacity)
- 游标只有配合基于排序键的查询才避免深偏移成本；仅编码页码没有该优势。它不自动提供快照一致性，排序字段更新或数据删除仍会影响遍历结果；需要固定结果集时另行设计快照机制。

下面展示按创建时间倒序翻页的 SQL 思路，假设两个排序字段均非空且稳定，`id` 唯一；命名参数按实际数据库驱动绑定，`:fetch_limit` 为已校验页大小加一：

```sql
SELECT id, name, created_at
FROM users
WHERE tenant_id = :tenant_id
  AND (
    created_at < :cursor_created_at
    OR (created_at = :cursor_created_at AND id < :cursor_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT :fetch_limit;
```

首屏省略游标条件，保留访问范围限制。查询多取一条判断是否还有下一页，但响应只返回页大小以内的数据；下一游标来自最后一条实际返回的记录。评估与筛选、排序匹配的索引，不直接把此示例当作完整实现。

沿用 `data` 包装的项目，最后一页可约定如下；客户端依据明确的结束标记停止，不能仅凭记录数少于页大小判断结束：

```json
{
  "data": [{ "id": "usr_123", "name": "张三" }],
  "meta": { "has_next": false, "next_cursor": null }
}
```

## 筛选、排序与字段选择

先定义受支持的查询能力，再选择一致的参数语法。以下为可选约定，实际请求通过 URL 编码器构造：

```text
GET /api/v1/orders?status=pending&customer_id=usr_123
GET /api/v1/products?price[gte]=10&price[lte]=100
GET /api/v1/products?category=books,games
GET /api/v1/products?sort=-created_at,-id
GET /api/v1/products?q=wireless+headphones
GET /api/v1/users?fields=id,name
```

- 明确多值筛选的 AND/OR 语义、分隔符转义、大小写、时间边界、空值和默认排序；精确匹配与模糊搜索分开定义。
- 筛选字段、运算符、排序字段及方向使用允许列表，值通过参数绑定传递，不将查询参数直接拼接进 SQL。
- `fields` 和 `include` 不能绕过字段及关联资源权限；限制可展开关系、深度和查询成本。无需求时不自动添加通用查询语言。

## 认证、授权与输入校验

- 沿用现有认证方案；Bearer 令牌通过 `Authorization` 传递，API 密钥使用约定的请求头，不放入 URL。明确哪些端点公开，不把所有接口默认改成需要登录。
- 对每次资源访问检查操作权限、对象权限和租户范围，包括列表、批量操作与关联资源。身份认证成功或 ID 难以猜测不能替代授权检查。[OWASP 对象级授权](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)
- 使用显式的输入、输出字段集合，避免将请求体直接写入模型，或将数据库对象原样返回。客户端不得通过 `role`、`tenant_id` 等字段提升权限。
- 区分解析失败、字段校验失败与业务冲突；检查请求体大小及集合长度。不要让非法 JSON 落入通用异常处理后变成 `500`。

## 幂等、并发与重试

- 对创建订单等重复执行代价较高的操作，按需求提供幂等键，例如项目约定的 `Idempotency-Key`；不能只读取请求头而不实现去重。
- 明确键的调用方与操作作用域、有效期、请求内容指纹、处理中状态和结果保留规则。同键同请求在约定有效期内复用结果，同键不同请求明确拒绝；并发同键请求须原子去重，并考虑业务写入与结果记录之间的故障恢复。
- 存在覆盖更新风险时，可用强 `ETag` 配合 `If-Match`，在写入时原子检查版本；前置条件失败返回 `412`，不能先检查再无条件写入。[条件请求](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)
- 仅对可重试故障采用有上限的退避与抖动，并遵守 `Retry-After`；自动重放前确认请求具备幂等保证，或原请求尚未执行。异步操作返回 `202` 后，还要定义任务的权限、状态和失败结果。

## 限流

根据请求成本、服务容量和产品要求定义限流主体、窗口、突发额度及端点差异，不照搬固定的每分钟次数。内部调用同样按实际容量设计保护措施。

触发限流时返回 `429`；能够给出合理等待时间时附带 `Retry-After`，格式为等待秒数或 HTTP 日期。区分调用方超额与服务整体不可用，不对所有情况使用同一错误码。[429 规范](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)

如果项目暴露 `X-RateLimit-*` 等字段，应记录其名称、单位和重置时刻含义；不要将服务商惯例描述为统一标准。

## 版本与兼容性

- 沿用现有版本方案。需要显式版本的新 API 可选择路径版本，如 `/api/v1/users`；选择请求头或媒体类型协商时，同步处理路由、缓存区分和文档。不为未版本化的既有接口擅自增加前缀。
- 删除或重命名字段、修改类型、增加必填输入、收紧校验、改变权限及默认排序，都可能破坏客户端。新增响应字段、枚举值或可选参数也要结合实际客户端和生成的 SDK 判断，不能一概视为兼容。
- 发生不兼容变更时提供版本隔离或明确的迁移方案；支持几个版本、保留多久由调用方依赖和维护能力决定，不预设统一数量或期限。
- 弃用时提供替代接口、迁移说明和时间安排。采用标准响应头时，`Deprecation` 使用 `@` 加 Unix 时间戳秒数，`Sunset` 使用 HTTP 日期，且下线时间不得早于弃用时间。弃用本身不改变接口行为。[Deprecation 规范](https://www.rfc-editor.org/rfc/rfc9745.html)
- `Sunset` 表达预期停止服务的时间，不规定届时必须返回 `410`；根据实际下线行为确定响应，并更新调用方文档。[Sunset 规范](https://www.rfc-editor.org/rfc/rfc8594.html#section-4)

## 验证与交付

按本次涉及的行为选择检查，不为简单命名或文档调整运行整套服务测试。实现或修改端点时，重点验证以下适用项：

- 成功、空结果、资源不存在，以及响应状态码、响应头和响应体是否符合契约。
- 非法 JSON、字段边界、只读字段及未认证、越权、跨租户请求。
- 分页边界、重复排序值、无效游标，以及约定的并发变化行为。
- 重复或并发请求、业务冲突、限流和条件更新，不只验证正常路径。
- OpenAPI 或等价契约文档、请求响应示例与实现一致；兼容性变化有明确说明。

设计任务给出可直接评审的方法、路径、权限、输入和关键响应；审查任务按影响说明具体位置与修正建议；实现任务说明改动和实际验证结果。未运行的检查如实标注，不把建议写成已完成事项。
